# Repository guide

## Purpose

Two goals, in this order of priority:

1. **Automated tests for improving generation skills** — above all
   [gyu-don/ogiri-ai](https://github.com/gyu-don/ogiri-ai), where an agent
   revises the 大喜利 skill and needs checks it can run without a human.
   These live in `skills/` and are Jev-only: a check goes there only once it
   agrees with human judgments.
2. **Research on measuring funniness by machine.** Nothing that asks "is it
   funny" agrees with the human labels yet. Those judges live in `research/`
   and are never used as automated tests.

Write evaluators as reusable functions of `(topic, answers)`, not tied to
ogiri-ai's output shape.

A tool is used in one of two places, and they ask different things of it
(`src/validation/judges.ts`, shown in `STATUS.md`):

- **Improvement loop** — runs without a human. Cheap, repeatable, and says
  what to fix. Weak agreement with the human is acceptable; a bias is not,
  because the loop optimises whatever it can measure.
- **Final check** — once, before a version is adopted. Only what agrees with
  the human's verdict on versions belongs here. Today that is the blind
  human comparison in the inbox, plus hard checks (form, length, duplicates
  within one output). Adoption rule (owner, 2026-11-16): no お題 where the
  human preferred the old version = adoptable; any loss = back to the ledger.

## Layout

- `skills/<name>/` — one automated-test skill, fully self-contained
  (`SKILL.md`, `package.json` with only `@typesafe-ai/sdk`,
  `scripts/evaluate.ts`, `assets/samples.json`), because installing copies
  exactly this directory. Scripts resolve `../assets/*.json` relative to their
  own file, fail loudly with the fix when the SDK isn't installed or
  `TYPESAFE_API_KEY` is missing, and run directly on Node >= 22.6 (no build).
  `SKILL.md` must state the human agreement it was validated at.
  `.claude/skills/<name>` symlinks here — edit the `skills/` copy.
- `research/<name>/` — judges still under validation; status and promotion
  criteria in `research/README.md`. Not installable. `criterion-count` is
  the one loop instrument here: it counts answers matching a yes/no question
  an experiment wrote, and each question needs a human spot check.
- `STATUS.md` — where things stand, generated by `npm run status`: each
  judge's agreement with the human (all labels and labels its questions were
  not written from), the human evidence on hand, and the hypothesis ledger
  with verdicts. Read it first. Never hand-edit it, and don't copy its
  numbers into other documents — point to it. (`SKILL.md` is the exception:
  it is installed alone, so it states its own agreement.)
- `data/human-evals/<source>/` — human judgments, the ground truth. Follow
  `data/human-evals/README.md` when adding a session.
- `data/inbox/<source>/` — requests waiting for the human: blind final
  checks and criterion spot checks. Agents add with `npm run inbox:add` and
  never wait; the human judges with `npm run inbox`, which writes the
  session, links the ledger and rebuilds `STATUS.md` (`data/inbox/README.md`).
- `data/ledger/<source>.json` — one entry per hypothesis: what was tried on
  the generator, or what the rater seems to like, and its status. No concrete
  answers, no numbers (`data/ledger/README.md`). Add an entry when an
  improvement round ends; start a new round by citing entries.
- `src/validation/` — measures judge agreement with human labels
  (procedure in `src/validation/README.md`). `judges.ts` is the one list of
  judges and the date each one's questions were fixed.
- `src/status/` — builds `STATUS.md` from the latest validation, the human
  labels, the ledger and the inbox.
- `src/inbox/` — the inbox: request checks, blinding, the local page, and
  the conversion of a judgment into a human-eval session.
- `reports/` — generated output only; never hand-edit except `notes.md`.
- Deterministic checks (char counts, punctuation, regex) go in plain code,
  never as a Jev question.

## Commands

- `npm install`, `npm run check` (type-check), `npm test` (no API: runs the
  judge scripts against a fake SDK in `test/fake-sdk/`)
- `doppler run -- npm run audit:overlap-check` / `audit:trait-check`
- `doppler run -- npm run validate:jev -- reports/validation/<date> [runs]`
- `npm run validate:blind -- make|unblind ...`, `npm run validate:agreement -- reports/validation/<date>`
- `npm run inbox:add -- <request.json>` to queue a blind comparison for the
  human, `npm run inbox:spot-check -- <criterion-count output> <id>` to queue
  a spot check, `npm run inbox` (the human) to judge what is waiting
- `npm run status` to rebuild `STATUS.md` (no API). Run it after a
  validation, a new human-eval session or a ledger edit; `npm test` fails
  while `STATUS.md` is out of date.
- `npx skills add . -s <name>` to install a skill locally (`--list` to see what's found)

`TYPESAFE_API_KEY` comes from Doppler — never print/commit it or add a
`.env`; anything touching the TypeSafe API runs under `doppler run --`.
Use `jj`, not `git`.

## Jev conventions

- `@typesafe-ai/sdk`'s `TypeSafeClient`, model alias `jev-latest` unless an
  experiment documents why it pins a version.
- One atomic question per axis (`choice` / `score` / `noul`); split any axis
  that's really two independent factors.
- Batch independent questions about the same state into one call.
- Calibrate thresholds against real measured examples.
- Before changing SDK/API usage, check https://docs.typesafe.ai/sdk/javascript
  (and `/models`, `/api`).

## Change workflow

After code changes: `npm run check`, `npm test`, and if request shape changed, one real
`doppler run --` call to confirm the response still parses.

After any change to a judge (`skills/` or `research/`), run validation
(`src/validation/README.md`) and compare `summary.md` with the previous run.
A change is an improvement only if human agreement goes up. For `skills/`,
nothing may regress — in particular `overlap-check` `false flags` must stay 0.
Agreement on the labels a question was written from is optimistic; the
未使用ラベル section of `summary.md` is the number that counts, and a
question rewritten from the labels needs its `frozen` date in
`src/validation/judges.ts` moved forward.
