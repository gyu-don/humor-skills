# 判定の受付箱

人間に判定してほしいものを、エージェントがここに置く。人間は時間のあるときに1画面で開いて、溜まった分をまとめて判定する。
エージェントは判定を待たない。置いたら次の作業に進む。

```
data/inbox/
└── <source>/<id>.json     判定待ちの依頼（判定が済むと消える）
```

判定が済むと、結果は `data/human-evals/<source>/<判定日>-<id>.json` と `.md` になり、依頼はここから消える。`STATUS.md` の「判定待ち」に今の一覧が出る。

## 人間がやること

```
npm run inbox
```

表示されたアドレスをブラウザで開く。どちらがどの版かは、送信したあとに表示される。終わったら Ctrl-C で止める。

- **最終チェック**: お題ごとに A と B の回答が10本ずつ並ぶ。セットとして面白い方（A・B・引き分け・スキップ）を選ぶ。特に良い回答に ◎、悪い回答に × を付けられる（任意）
- **狙いの質問の抜き取り確認**: 回答1本ずつ、表示された質問に「はい・いいえ・どちらとも」で答える

送信すると、次のことが自動で起きる。

1. セッションの `.json` と `.md` が `data/human-evals/` に書かれる
2. 最終チェックなら、依頼が指していた台帳の行（`data/ledger/`）に、その比較が足される
3. `STATUS.md` が作り直される。台帳の行に、勝ち・引き分け・負けと、採否の規則の結果が出る

**採否の規則**（2026-11-16、オーナー決定）: 最終チェックで、変更前の版が選ばれた題が1つもなければ採用可。1つでもあれば台帳に戻す。引き分けとスキップは負けに数えない。

## エージェントがやること

### 最終チェックを頼む

版を採用する前に1回行う。出す前に、機械の不合格条件（形式・文字数の違反がないこと、1回の出力内に被りがないこと）を確かめておく。

1. 台帳に、その変更の行があることを確かめる。なければ先に足す（`data/ledger/README.md`）
2. 依頼のファイルを書く

   ```jsonc
   {
     "id": "cross-run-dedup",            // 小文字・数字・ハイフン。セッションのファイル名になる
     "kind": "final-check",
     "source": "ogiri-ai",
     "created": "2026-11-16",
     "ledger": "performance-finish",     // 台帳の行の id（kind が change のもの）
     "description": "何と何を比べるか。人間には判定のあとで見せる",
     "generator": "claude-opus-5-5 / high",
     "candidate": "変更後の版（jj の change や bookmark）",
     "baseline": "変更前の版",
     "machine": "不合格条件の結果（任意）。例: 形式違反 0、出力内の被り 0",
     "topics": [
       {
         "key": "codex",                 // 小文字・数字・ハイフン
         "topic": "Codexのイケてる使い方",
         "candidate": [["…5本"], ["…5本"]],   // 生成1回ごとの回答。1回以上
         "baseline": [["…5本"], ["…5本"]]     // ちょうど2回（独立に生成する）
       }
     ]
   }
   ```

   `topics` の各要素は、`trait-check` の `scripts/versions.ts` の入力と同じ形（`key` が余分にあるだけ）
3. 受付箱に入れる

   ```
   npm run inbox:add -- <依頼.json>
   ```

   形式を確かめ、伏せ方を決める `seed` を足して `data/inbox/<source>/<id>.json` に置く。`data/inbox/` にファイルを直接コピーしない（`seed` がないと読み込めない）
4. 人間を待たずに次へ進む。台帳の行は `open` のままにしておく

### 狙いの質問の抜き取り確認を頼む

`criterion-count` の質問を初めて使うとき、または書き直したときに行う。

```
npm run inbox:spot-check -- <criterion-count の出力.json> <id>
```

数えた回答から20本までを選んで依頼を作り、受付箱に入れる（`research/criterion-count/SKILL.md`）。

## 伏せ方

- どちらの版を A にするか、回答をどの順に並べるかは、依頼の `seed` から決まる。`seed` は受付箱に入れた時点で決まるので、対応表は判定の前に存在する
- 画面に渡すのは、お題と回答の文面だけ。版の名前、実行番号、依頼の説明、台帳の行、判定器の確率は渡さない（`test/inbox.test.ts` が確かめている）
- 依頼のファイルそのものを開けば版は分かる。伏せているのは画面だけ
- 評価者が実験の狙いを知っていれば、内容から版を推測できることはある。これは伏せられない
