# 評価器の分類と Jev 版の改善 2026-09-24 — 所見

数値は [summary.md](summary.md)（`npm run validate:agreement -- reports/validation/2026-09-24` で再生成できる）と、候補の質問を試した [candidates/summary.md](candidates/summary.md)（質問文は [candidates/questions.md](candidates/questions.md)）。
正解データは前回と同じ `data/human-evals/ogiri-ai/`。今回は一対比較の検証を加えた。

## 目的

各スキルを次の3つに分類する。あわせて、Jev の質問文の改善で人間との一致が上がるものは改善する。

1. Jev による評価が妥当に機能する
2. Jev では妥当でないが、Claude による評価なら妥当に機能する
3. Claude でも不十分で、人間の評価が必要

ogiri-ai のスキルを自動で改善するときに使えるかを重視した。

## 条件

- Jev 版: 各スキルの `scripts/evaluate.ts` を2回実行した。今回から `humor-rank` も入れた。人間の好みがわかっている同じお題の回答ペア60組を判定させた。内訳は、同じセット内の当たり×外れの50組と、人間が直接比べた13組（重複を除く）
- プロンプト版: `humor-rank` は Sonnet のサブエージェント2回（`SKILL.md` どおり）。比較用に、ルーブリックなしの「どちらが面白いか」を1回。入力は [blind/pairs.md](blind/pairs.md) で、A/B の順番はランダム、出所は伏せた
- `cluster-fit-check` は Jev 版を1回
- `diversity-check`・`humor-eval`・`fun-check` のプロンプト版は再実行していない。前回（[2026-09-23](../2026-09-23/notes.md)）の結果を使う

## Jev 版の変更

| スキル | 変更 | 前 → 後 |
|---|---|---|
| `fun-check` | `noPictureRisk`: 「具体的な場面が頭に浮かばないか」→「質感のある具体的な物・起きている現象・制度や設備の具体的な異常が出てくるか」（コードで反転） | AUC 0.60 → 0.66、セット 3/7 → 6/7 |
| `fun-check` | `lengthRisk`: 「3割以上削れるか」→「同じ着眼点を説明的・遠回しに言っているか」 | AUC 0.57〜0.59 → 0.62〜0.64、セット内 0.55 → 0.60 |
| `fun-check` | 合計（`sumRisk`、検証スクリプト側の値） | AUC 0.60 → 0.64〜0.67、セット 3/7 → 6/7 |
| `humor-rank` | 勝敗を総合の1問ではなく、「具体物・現象がはっきりあるのはどちらか」と「直球で短く言い切っているのはどちらか」の平均で決める。総合の1問は `holisticProbA` に残す | セット内 0.54 → 0.66、13組 0.46〜0.50 → 0.77、確信度の高い判定 0.38〜0.47 → 0.73 |

どちらも、人間の過去の所見（[findings.md](../../../data/human-evals/ogiri-ai/findings.md)）の「概念は絵じゃない（質感のある物か起きている現象を連れてこい）」（07-11）、「制度・設備・役割の具体的な異常を一つ置いた短い回答が強い」（09-22）、「直球で言い切る短い表現が説明的な言い換えより強い」（09-15）を、1問ずつの記述的な質問にしたもの。

採用しなかった候補（[candidates/questions.md](candidates/questions.md)）:

- 面白さを直接聞く質問は、どの言い方でも逆向きになった。「どちらが面白いか」「客席がより大きく笑うのはどちらか」「声を出して笑う確率」は、確信度の高い判定ほど外れる（0.32）
- `humor-rank` の Step 2 で最優先の「回収可能性」を単独で聞くと 0.36 で、人間と逆だった。逆向きの指標を反転して足すと数値はさらに上がる（0.74）が、過学習の典型なので採らなかった
- 「ひねりなし」「滑り」の言い換えは試していない。人間の当たりに「一段しか跳んでいなくても大胆な回答」が多いことと、構成概念そのものが食い違っているので、言い方の問題ではないと判断した

## 注意

- **過学習:** 採用した質問は、この検証データを見て書かれた人間の所見から作った。同じデータで一致が上がるのは当然の面がある。部分的な反証の機会として、09-15 のセッション（所見の元ではない）で `concrete` の AUC は 0.83〜0.86 だった。ただし回答10本、当たり3本しかない。別のお題で新しい人間の判定を取るまでは、改善幅は楽観的な値と読む
- `pairs` 列（13組）は、確率がほぼ0.5の判定が多いと実行ごとに入れ替わる（`noPictureRisk` は 0.54〜0.69）。13組の数字で細かい差を比べない
- **Goodhart のリスク:** 「具体物」「直球」は、07-11 でアトラクター化した「痕跡＋小さい数字」と同じ種類の、勝ちパターンから抜き出した性質である。ogiri-ai がこの数値を最大化するように改善すると、同じ型への収束が起こりうる。「前の版より下がっていないか」という下限の確認に使い、最大化の目標にしない。被りチェックと人間の抜き取り確認を組み合わせる
- プロンプト版の判定モデルは Sonnet だけ。Opus などは未検証

## ogiri-ai への反映の提案

gate check の3段階（[2026-09-23-overlap](../2026-09-23-overlap/notes.md)）に、次のように入れる。

- **絶対条件（変更なし）:** お題の形式、「」と文字数（コード）、Jev の `nearDuplicates`
- **変更前の版との相対比較:** `fun-check` の `noPictureRisk`・`lengthRisk` のセット平均が有意に悪化していないか、`humor-rank` で新旧の回答を総当たりしたときの勝率。どちらも「下がったら差し戻す」に使い、「上がったから採用」には使わない
- **使わない:** `humor-eval` の点数、`fun-check` のベタ・ひねりなし・滑り、`cluster-fit-check`

## 評価の作り方についての提案

今回の作業からわかったこと:

1. **「面白いか」ではなく「性質Xがあるか」を聞く。** 記述的な質問は Jev でも安定し（r≥0.97）、人間の判定と照らし合わせられる。「面白さ」を直接聞く質問は、Jev でも Claude でもチャンスレベルか逆向きだった。人間の所見 → 1問の記述的な質問 → 人間ラベルとの一致を測る → 通ったものだけを相対比較に使う、という流れで評価器を増やすとよい
2. **人間の失敗パターンの所見を、そのまま検出器にする。** findings.md の「概念だけ」「誇張だけ」「説明的な言い換え」「形式外れ」は、どれも1問の noul にできる。生成側の改善でよく起きる失敗（アトラクター化、概念への収束）を検出する方が、面白さの絶対評価より当たりやすい
3. **正解データの取り方を一対比較に寄せる。** `npm run validate:blind -- make` が `pairs.md`（人間の好みがわかっているペア）を出すようにした。新しい人間評価も、同じお題の5本のセットを全部残したうえで、新旧の版の回答を A/B で比べる形で取ると、評価器の検証にもそのまま使える。今回の改善を確かめるには、検証に使っていない新しいお題で 50〜100組ほど取るのが次の一手
4. **確信度の高い判定だけを見る列を作った。** `agreement` の一対比較の表の `confident` 列。これが平均より低い評価器は、自信を持って間違える（人間と逆の好みを持つ）ので、足切りにも使えない
5. **指示の遵守と結果の良さを分ける。** `src/ogiri-ai/rule-audit.ts` のような「SKILL.md の指示が守られたか」の測定は、Jev に向いていて、自動改善の中で「指示が効いていないのか、指示が効いても面白くならないのか」を切り分けられる。ただしこれも、判定の正しさを小さな手ラベルで一度確かめておく

研究（目的2）の観点では、Jev の「面白さ」の判断がこの評価者とは一貫して逆向き（0.37〜0.44）だったことが目立つ。整合的で説明しやすい回答を高く評価する LLM の傾向（`fun-check` の SKILL.md の注記）と合っている。ただし評価者1人・小さいサンプルなので、逆向きの信号をそのまま使うことはしない。
