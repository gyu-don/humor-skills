# 研究用の判定器

`skills/` に入れるのは、人間の判定と一致し、自動テストに使えるものだけ（`overlap-check`・`trait-check`）。
このディレクトリには、まだ人間の判定と一致していないが、検証を続けるものを置く。
インストール対象ではない（`npx skills add` や `/plugin install` では入らない）。スクリプトはリポジトリ直下の `node_modules` を使う。

どれも `npm run validate:jev` で毎回検証される。プロンプト版のあるもの（SKILL.md の手順を Claude が実行するもの）は、`npm run validate:blind` の入力をサブエージェントに渡して検証する（`src/validation/README.md` を参照）。

| 判定器 | 旧名 | 測るもの | 2026-09-24 の状態 |
|---|---|---|---|
| `funniness-score` | `humor-eval` | 面白さの6軸採点（Jev・プロンプト） | Jev は逆向き（AUC 0.37〜0.44）、プロンプトはチャンスレベル |
| `risk-flags` | `fun-check`（の残り） | ベタ・ひねりなし・共感・認知度・滑り・相対典型性・シュール手癖（Jev・プロンプト） | チャンスレベル。ひねりなし・滑りは逆向き |
| `diversity-check` | 同じ | お題の分解軸の数（プロンプト） | 収束の判別 AUC 0.49 |
| `cluster-fit-check` | 同じ | 文献由来のユーザークラスタ別の嗜好への適合（Jev・プロンプト） | 検証できていない（下記） |

ベースライン（`src/validation/run-jev.ts` の中にある）: ルーブリックなしの「どれくらい面白いか」（`naive`）と「どちらが面白いか」（`naive-pairwise`）。
面白さを測る判定器は、少なくともこの2つと文字数（`baseline −length`）を上回る必要がある。

`skills/` に移す条件: 人間の判定での一致が、95%区間で偶然を上回り、2回の実行で安定し（r≥0.95）、検証に使っていない新しい人間評価でも再現すること。

## `cluster-fit-check` の検証に必要なもの

クラスタは「評価者によって好みが違う」ことのモデルなので、評価者が1人の今のデータ（`data/human-evals/ogiri-ai/` は全部 `rater: repo-owner`）では確かめられない。
今のデータで C0〜C6 のスコアと当たりを比べると、AUC 0.45〜0.58 で、セッションごとに向きが変わる。ただしこれは、評価者1人の好みがどのクラスタにも当たらないことしか意味しない。

検証するには、次の人間データを足す。

1. **複数の評価者による同じ回答の判定。** 同じ `pairs.md`（`npm run validate:blind -- make` が出力する一対比較）を、評価者ごとにブラインドで判定する。1人1セッションとして `data/human-evals/<source>/<date>-<rater>.json` に置き、`rater` を分ける。目安は5人以上、1人50組以上
2. **評価者の割り当てと予測。** 評価者ごとに、判定の半分で「どのクラスタのスコアが一番その人の好みに合うか」を決める。残りの半分で、そのクラスタのスコアがその人の好みを偶然より当て、他のクラスタのスコアより当てるかを見る
3. **特徴抽出の正しさ（評価者が1人でもできる）。** クラスタの重みの前に、Jev の特徴判定（自虐・シュール・擬人化など16個）が合っているかを、回答50本ほどの手ラベルで確かめる

`src/validation/labels.ts` は今は評価者を区別していない。1 のデータが入った時点で、`agreement.ts` に評価者別の集計を足す。

もともと ogiri-ai の生成スキルに書いていた。クラスタを意識してばらした方が面白くなったが、アトラクター化を避けるために評価側に移した経緯がある。
検証できれば、「セットが特定のクラスタに偏っていないか」という多様性のチェックとして、生成スキルの自動改善に戻せる可能性がある。
