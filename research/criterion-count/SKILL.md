# 狙いの数え上げ（研究用）

生成スキルへの変更には、たいてい「こういう回答を出したい」「こういう回答を減らしたい」という狙いがある。
その狙いを yes/no の質問1つにして、変更前と変更後のセットでそれぞれ何本当てはまるかを数える。

## 位置づけ

- 改善ループの計器。変更の狙いが出たかを、人を待たずに確かめるために使う
- 面白さは測らない。狙った型が増えても、面白くなったとは限らない。採用するかどうかは、人間のブラインド比較で決める
- 数は質問の出来で決まる。質問ごとに、人間の抜き取り確認を通してから頼る（下の「抜き取り確認」）

## 使い方

リポジトリ直下で実行する（`npm install` 済みであること）。

```
doppler run -- node research/criterion-count/scripts/evaluate.ts <入力.json> [出力.json]
```

- 入力: `{"criterion": {"question": "...", "true": "...", "false": "..."}, "sets": [{"id": "candidate-r1", "topic": "...", "answers": ["...", ...]}, ...]}`（見本は `assets/samples.json`）
  - `sets` は、版と実行ごとに1セットにする。`id` がなければ `set-1`、`set-2`… と振る
- 出力: `summaries[]` にセットごとの `count`（yes の確率が 0.5 以上の本数）と `total`、`rows[]` に回答ごとの確率 `yes`

## 質問の書き方

- **1問で1つの性質だけを聞く。** 「AかつB」は2問に分けて、別々に数える
- **回答1本について、見れば分かることを聞く。**「面白いか」「うまいか」は聞かない
- **yes と no の意味を必ず書く。** 定義がないと、判定器は「当てはまる」と答えすぎる（2026-10-17 の確認で、人間が「いいえ」とした回答に 0.5〜0.8 を付けた）。紛らわしい例は no の定義に入れる
- **数えれば分かることは、コードで数える。** 文字数、文字種、括弧の数は判定器に聞かない。形式を実際に外しているかどうかはコード（`src/mechanical/check_form.py` など）で調べ、判定器には意味の部分だけを聞く

## 抜き取り確認

質問を初めて使うとき、または書き直したときに行う。

1. 数えた結果から、人間に確かめてもらう回答を抜き出して受付箱に置く

   ```
   npm run inbox:spot-check -- <出力.json> <依頼のid>
   ```

   yes とされた回答、確率が 0.5 に近い回答、no とされた回答から、合わせて20本まで選ぶ
2. 人間が受付箱の画面（`npm run inbox`）で、同じ質問に「はい／いいえ／どちらとも」で答える。判定器の答えは見せない
3. 一致した本数が `STATUS.md` の「狙いの質問の抜き取り確認」に出る。食い違った回答を見て、質問か定義を直す。直したら数え直し、もう一度確かめる

確認が済むまでの数は、仮の値として記録する。

## 信頼度

ツールとしての一致率はない。質問ごとに抜き取りで確かめる。

最初の試行（2026-11-16）: 「7文字で」と指定するお題の40本（2つの実験の、変更後と変更前）で、「形式の条件を1つだけ破っていて、破ったこと自体が答えになっているか」を数えた。

- 実験の監査で受理されていた2本を、どちらも yes とした。変更前の版の20本は、すべて no だった
- 文字数は守っているが条件に触れている回答2本を、yes とした（誤り）。判定器は文字数を数えられない
- 40本中36本が、実験の記録にある手作業の監査と一致した。監査を付けたのは生成側のエージェントで、人間の評価者ではない

上の「数えれば分かることは、コードで数える」は、この誤りから足した規則。
