# 性質チェック

## 準備

- Node.js 22.6以上、環境変数 `TYPESAFE_API_KEY`
- 初回のみ、このディレクトリで `npm install`

## 回答ごとの採点

```
node scripts/evaluate.ts <入力.json> [出力.json]
```

- 入力: `{"topic": "...", "answers": ["...", ...]}`、または複数セットの配列（見本は `assets/samples.json`）
  - 配列の各要素の `id`・`label` は任意。`id` がなければ `set-1`、`set-2`… と位置で振る。結果は `id` で引くので、`id` が重複していればエラーで止まる
- 出力: `summaries[].means` にセット平均、`rows[].traits` に回答ごとの値
  - `concrete`: 具体的な物・現象・異常が出てくる確率。高いほど良い
  - `indirect`: 説明的・遠回しに言っている確率。低いほど良い

## 一対比較

```
node scripts/compare.ts <入力.json> [出力.json]
```

- 入力: `{"topic": "...", "answerA": "...", "answerB": "..."}`、または配列（見本は `assets/pairs.json`）
  - `id`・`label` の扱いは回答ごとの採点と同じ
- 出力: `results[].probA`（A の方が良い確率）、`winner`（`A` / `B` / `draw`）、`criteria`（`concrete` と `straight` それぞれで A が勝つ確率）

## 版の比較

```
node scripts/versions.ts <入力.json> [出力.json]
```

- 入力: `{"topic": "...", "baseline": [[1回目の回答...], [2回目の回答...]], "candidate": [[...], ...]}`、またはお題ごとの配列。変更前（`baseline`）は同じお題で独立に2回生成する。変更後（`candidate`）は1回以上
- 出力:
  - `overall`: 全題をまとめた読み。`concrete` と `indirect` それぞれについて、変更後がどれだけ悪いか（`worsening`）と、それが偶然でも起きる割合（`p`）。`flagged` は p < 0.05 の性質の一覧
  - `results[]`: お題ごとの同じ読み（診断用）、`explanatory`（変更後の回答のうち `indirect` が 0.2 以上のもの）、回答ごとの値

`p` は、お題の中で「変更前・変更後」のラベルを入れ替えたとき、変更後が実際と同じかそれ以上に悪く見える入れ替えの割合。全題をまとめて1つ出すので、題ごと・指標ごとに何度も判定して偶然に引っかかることがない。1題10本ずつでは、題ごとの読みが 0.05 を切ることは少ない。

## 読み方

改善ループの中で、次の2つに使う。

- **直す候補を見つける。** `explanatory` に挙がった回答は、同じ着眼点をもっと直球に言えないかを見る。`indirect` が 0.2 以上の回答が人間に選ばれることは少なかった（人間のラベル170本で、0.2 以上の29本中3本、未満の141本中32本）
- **性質が動いたかを見る。** `overall` の `flagged` に性質が入ったら、変更がその性質を悪い方に動かした合図として、回答を見る

版を採用するかどうかには使わない。採否は、人間のブラインド比較で決める（humor-skills の受付箱、`data/inbox/README.md`）。

- 合図は差し戻しの理由にしない。人間がセット単位で比べた7題で、この読みが人間の判定を当てるかは `STATUS.md` に出る。人間が変更前を選んだ版を、見分けられてはいない
- 値が良くなったことを採用の理由にしない。この値を上げることを目標にすると、回答が同じ型に収束する
- 1本の回答の合否にも使わない
- 水準 0.05 と閾値 0.2 は、結果を見てから動かさない

以前は、変更前の1回目と2回目の差をノイズ幅として、それを超えた悪化を回帰と判定していた（`gate.ts`）。1組の実行から測った幅は .002 のように小さく出ることがあり、人間が引き分けとした5題中4題を回帰と判定した（humor-skills `reports/validation/2026-11-15`）。一対比較の総当たりは、回答ごとの `concrete`・`indirect` と同じ性質を聞き直すもので、呼び出しが10倍以上かかるので、版の比較からは外した。2つの回答を直接比べたいときは `compare.ts` を使う。

## 苦手なもの

- お題の条件そのものを使う回答（文字数を指定するお題で、文字数そのものに触れる回答など）は、物も出来事も置かないので `concrete` が低く出る。2026-11-08 の7文字のお題では、変更後の `concrete` が .568、変更前が .68〜.72 だった。こうした型の回答を増やす変更は、面白さと関係なく `concrete` に合図が出やすい。この型を狙う変更では、型に当たる回答の本数を別に数え（humor-skills `research/criterion-count`）、読みと並べて報告する

## 信頼度

人間の判定との一致は、質問を作るのに使ったラベルと、その後に足したラベルで分けて読む。0.5 が偶然、角括弧は 95% 区間。

| 指標 | 質問を作ったラベル（2026-09-23 まで、75本） | その後のラベル（95本、当たり13本） |
|---|---|---|
| `concrete` | AUC 0.67〜0.68 | AUC 0.51 [0.36, 0.67] |
| `indirect` | AUC 0.56〜0.64 | AUC 0.71 [0.54, 0.87] |
| 一対比較（`probA`） | セット内 64〜66%、人間の直接比較 10/13 | セット内 60% [45, 74]（40組）、人間の直接比較 2/7 |
| 一対比較のうち `straight` | - | セット内 68% [52, 80]（40組） |

- `concrete` は、その後のラベルでは偶然と区別できていない。`indirect` と一対比較の `straight` は偶然を上回った
- どちらも区間が広い。当たり13本では、効くとも効かないとも言い切れない
- 2回の実行間の相関は r≥0.97
- 左の列は 2026-09-24〜2026-11-09 の検証、右の列は 2026-11-15 の検証（humor-skills `reports/validation/2026-11-15/notes.md`）。最新の値は humor-skills の `STATUS.md` にある
