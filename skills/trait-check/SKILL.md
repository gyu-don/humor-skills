# 性質チェック

## 準備

- Node.js 22.6以上、環境変数 `TYPESAFE_API_KEY`
- 初回のみ、このディレクトリで `npm install`

## 回答ごとの採点

```
node scripts/evaluate.ts <入力.json> [出力.json]
```

- 入力: `{"topic": "...", "answers": ["...", ...]}`、または複数セットの配列（見本は `assets/samples.json`）
  - 配列の各要素の `id`・`label` は任意。`id` がなければ `set-1`、`set-2`… と位置で振る。結果は `id` で引くので、`id` が重複していればエラーで止まる
- 出力: `summaries[].means` にセット平均、`rows[].traits` に回答ごとの値
  - `concrete`: 具体的な物・現象・異常が出てくる確率。高いほど良い
  - `indirect`: 説明的・遠回しに言っている確率。低いほど良い

## 一対比較

```
node scripts/compare.ts <入力.json> [出力.json]
```

- 入力: `{"topic": "...", "answerA": "...", "answerB": "..."}`、または配列（見本は `assets/pairs.json`）
  - `id`・`label` の扱いは回答ごとの採点と同じ
- 出力: `results[].probA`（A の方が良い確率）、`winner`（`A` / `B` / `draw`）、`criteria`（`concrete` と `straight` それぞれで A が勝つ確率）

## 版の比較（回帰判定）

```
node scripts/gate.ts <入力.json> [出力.json]
```

- 入力: `{"topic": "...", "baseline": [[1回目の回答...], [2回目の回答...]], "candidate": [[...], ...]}`、またはお題ごとの配列。変更前（`baseline`）は同じお題で独立に2回生成する。変更後（`candidate`）は1回以上で、まとめて1つのセットとして扱う
- 出力: `results[]` にお題ごとの `concrete`・`indirect`・`compare` の判定（`worsening` が悪化幅、`noise` がノイズ幅）と、`regressed`（ノイズ幅を超えて悪化した指標の一覧）。回答ごとの値と、全ペアの `probA` も残す

## 合否の決め方

同じお題で変更前の版と変更後の版の回答を比べる（`gate.ts`）。次のどれかが、ノイズ幅を超えて悪化したら差し戻す。

- `concrete` のセット平均が下がった。ノイズ幅は、変更前の1回目と2回目のセット平均の差
- `indirect` のセット平均が上がった。ノイズ幅は同じく、変更前の2回の差
- 変更後（A）× 変更前（B）の全ペアを一対比較して、平均 `probA` が0.5を下回った。ノイズ幅は、変更前の1回目（A）× 2回目（B）の総当たりでの |平均 `probA` − 0.5|

ノイズ幅を置くのは、同じ版でも生成のたびに値が動くからだ。ogiri-ai の 2026-11-08 の実験では、変更前の1回目と2回目の総当たりで、平均 `probA` は 0.420〜0.563（0.5 からのずれは最大 .08）だった。差の向きだけで判定すると、ノイズで差し戻すことになる。

- 引き分けを除いた勝率では判定しない。同じ版の1回目と2回目でも 0.20〜0.80 まで振れた。出力には診断用に残す
- ノイズ幅は、結果を見てから広げない
- ノイズ幅は1組の実行から測った運用上の許容幅で、信頼区間ではない

**検証の状況（暫定）:** 悪化を検出できるかは、まだ確かめていない。人間がセット単位で比べた5題（2026-11-08、ブラインドは2題）には、人間が変更前の版を選んだ題がなかった。人間が引き分けとした4題では、ノイズ幅なしの規則はいずれかの指標で4題とも回帰と判定し、ノイズ幅ありの規則は3題を回帰と判定した（指標ごとに1題ずつ）。人間が変更後の版を選んだ1題は、どちらの規則でも回帰としなかった。1組の実行から測ったノイズ幅は、.002 のように小さく出ることもある（humor-skills `reports/validation/2026-11-09`）

悪化の検出にだけ使う。値が上がったことを採用の理由にしない。この値を最大化させると、回答が同じ型に収束する。
1本の回答の合否にも使わない。

## 苦手なもの

- お題の条件そのものを使う回答（文字数を指定するお題で、文字数そのものに触れる回答など）は、物も出来事も置かないので `concrete` が低く出る。2026-11-08 の7文字のお題では、変更後の `concrete` が .568、変更前が .68〜.72 だった。こうした型の回答を増やす変更は、面白さと関係なく `concrete` で回帰と判定されやすい。この型を狙う変更では、型に当たる回答を手で数え、判定と並べて報告する

## 信頼度

人間の判定との一致（2026-09-24）は次のとおり。質問を作ったのと同じデータで測った値なので、楽観的に読む。

- `concrete`: AUC 0.67
- `indirect`: AUC 0.62〜0.64
- 一対比較: 66%

2回の実行間の相関は r≥0.97。

2026-11-09 に同じラベルで測り直すと、`concrete` は AUC 0.68、一対比較は 64%（2026-09-25 の再実行と同じ）で、ほぼ変わらなかった。`indirect` は AUC 0.56 に下がった。スクリプトの出力は変更の前後で変わっていないので、`jev-latest` 側の変化とみられる。ラベルを170本に増やすと、`concrete` は AUC 0.62、`indirect` は 0.60。
